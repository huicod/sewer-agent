# 管网检测 Agent：总体开发计划

更新：2026-09-09；负责人：huicod；状态：用户已批准，M0 开发中；活动任务与验证记录见 .trellis/。

## 1. 目标与范围

交付能够实际运行的完整 Agent 软件原型，而非 YOLO26 调参或训练项目。采用现有五类权重，靠多模型协作、证据复检和可靠工作流改善系统能力；效果必须实测，不预先保证准确率提升。

需求与运行协议以[主方案](../vlm_review/VLM_YOLO_ARCHITECTURE_AND_RESEARCH_SUMMARY.md)为准；本文件是唯一总体开发计划。研究文档不自动成为开发任务。

- 输入：CCTV 单张图片或上传的离线视频，加自然语言任务；不含实时流、机器人控制或外部传感器。
- 主类：PL、BX、FS、BLOCK、AJ。可以输出正常；其他疑似缺陷进入人工确认，VLM 名称仅为建议。
- 首版包含图片、视频事件、条件式 VLM 复检、文本任务与报告、开放词表补召回；这些核心能力优先。
- 首版也包含条件式去雾/去模糊/超分、分割、相对深度，以及符合输入条件的比较、规范检索等工具；优先级较后，不取消。
- LLM、VLM 均通过 API 调用；本服务器运行后端与本地视觉模型。无标定、管径或实测深度，不输出毫米尺寸、真实堵塞率或无依据评级。
- 不训练新模型，不建设多租户、Kubernetes、通用 Agent 平台、自动标注训练闭环或额外硬件管线。

## 2. 拟定技术结构

使用模块化后端，不把每个工具拆成独立微服务：

```text
Web 界面 → FastAPI → Temporal 持久工作流
                         ├─ CPU/API worker：解码、LLM/VLM、结果与报告
                         └─ 单 GPU worker：可替换检测器、增强、分割、深度
              PostgreSQL：业务结果 / 审核记录
              本地持久目录：原始媒体 / 派生资产 / 证据与报告
```

- 后端 Python；界面拟采用 React + TypeScript + Vite，范围限于上传、进度、证据时间轴、审核和报告。
- Temporal 是唯一运行时编排器，执行顺序、重试、等待和恢复由它管理；LLM 只在受约束节点提出任务/工具计划。首版不叠加 LangGraph 或第二套任务队列。
- 模型、网络、文件 I/O 放在 Activities 中；Workflow 只做可重放编排。数据库业务视图不能自行推进另一套工作流状态。
- 单 GPU 默认串行调度重模型，按需加载/卸载；先实测显存和吞吐，再决定是否并发，不同时常驻所有模型。
- PostgreSQL 和 Temporal 均需真实持久化。当前无 Docker，M0 先验证可用的本机部署方式；若受容器限制不可行，报告具体阻碍后再调整，不静默换成不持久的开发服务。
- API 密钥由用户在服务器环境中配置；不写入文档、仓库或日志。模型供应商与 API 协议通过适配器解耦。

建议新增代码目录：`backend/src/pipe_inspector/`（api、contracts、workflow、agent、vision、storage）；`backend/tests/`；`frontend/`；`scripts/`。现有 `yolov26/` 材料保留，不迁移或重写训练代码。

## 5. 必须兑现的运行协议

- 主检测器通过 `DetectorAdapter` 输出标准坐标、五类映射、原始标签/分数和版本；工作流不得依赖 Ultralytics 对象。新模型接入需契约和同集回归，不承诺任意模型直接改名称即可替换。
- 所有媒体先做原始证据初查。VLM/YOLOE 按规则和文本触发；零候选仍有全图/周期审计，不能只复查已有 ROI。
- 视频首版默认对可解码帧做主检测，可分块/批处理；任何降采样模式必须显式报告覆盖与盲区。事件是可见时间段，不保证跨镜头回访仍识别成同一个物理缺陷。
- 工具采用白名单、输入输出 Schema、前置依赖、超时、有限重试与调用预算。LLM 不执行任意代码、不指定任意文件路径，也不自行套娃调用工具。
- 单事件暂定最多一次自动补证、一次开放扫描、两次语义复检；传输重试另设上限，均记录成本。后续根据测试调整配置，不无限循环。
- 资产和调用通过 ID、版本、数据库唯一键追踪，不默认计算输入/模型/Prompt 哈希。模型及计划版本在任务启动时固定；换版本以新任务或显式重处理运行执行。
- 本地结果幂等提交；API 超时可能已在供应商执行，不能保证零重复请求或零重复计费。对不确定调用状态记录并限制重试。
- 人工等待是非终态，不占 GPU。取消后保留已完成结果；重新继续取消任务应显式创建关联续跑，不悄悄复活已取消工作流。
- 文本动作全部成功才完成；必要步骤失败进入失败或不完整结果。可选能力缺失写明原因，不能把必需复检超时降级成“正常”。

## 6. 验收与测试边界

工程功能通过与模型效果提升是两套结论，分别记录：

1. 图片：五类、正常、其他待审、错报冲突、模糊不可判、文本要求和工具依赖均有固定案例。
2. 视频：短暂缺陷、跨块事件、重复画面、低质量时段、全程零结果；结果包含时间区间、证据、覆盖情况。
3. 恢复：杀 worker、重启 Temporal/数据库、API 超时/限流/非法 JSON、GPU OOM、人工等待后重启；任务不丢失，不重复落库，不隐瞒失败。
4. 替换：至少现有检测器和测试适配器通过同一契约；这证明软件解耦，不冒充第二个真实模型已经达到同等精度。
5. 效果：固定人工标注图片/视频，同一事件匹配标准下比较五类 precision/recall、事件误报/漏报及正常误判，同时报告人工审核量与每小时视频耗时/API 成本。
6. 工具：增强不能因分数变高就认定有效；分割/深度质量单独展示，缺标定不输出工程真值；所有后置工具至少有可重复成功案例和缺输入案例。

Sewer2403 的“五类负样本”可能含原始其他类别，不等于人工确认正常。需要小型真实正常/反光污渍/其他缺陷/困难正例回归集；没有足够数据时明确“功能通过，效果尚未充分验证”。

单元/契约测试使用本地替身避免反复付费；每个真实模型和 API 另做受控集成验证。性能与效果阈值在 M0/M3 用代表性数据确定，不编造吞吐、准确率或工期承诺。

## 7. 开发 Harness 与进度保存

需要轻量 harness：统一任务入口、可重复测试、工作记录和交接机制，不再开发一套“管理 Agent 的平台”。

- Trellis 初始化后管理正在执行的任务、必要 spec 与 workspace journal；总体范围和里程碑仍只维护本文件，不另建重复路线图。
- 每个任务只保存目标/范围、验收、当前状态、测试结果、jj change、阻碍与下一步；在阶段结束、阻塞或会话交接时更新，不为每条命令记流水账。
- jj 管本地 change/恢复；Git 用于远端兼容。开始新任务前检查差异，保留用户既有改动；不自动推送、建仓或重写既有历史。
- Superpowers 按需提供 TDD、调试和完成验证；不再创建第二套任务生命周期。grill-me 只追问会改变方案的未决问题，不重复已确认事实。
- stop-that-shit 约束过度开发、无必要依赖、重复核验和 token 浪费。日常只做改动相关测试与差异审查；不运行全量 SHA256 校验，不生成模型/输入哈希系统。
- 原 `SHA256SUMS.txt` 保留为历史交付记录，不重新计算、不作为开发验收门槛。软件包管理器自身的完整性检查不受此限制。
- Hook 是否强制生效需按现有手册由用户审阅信任；不能把“已安装”说成“已拦截”。没有 Hook 也遵守同样的任务边界。
- 开发进度保存与产品任务恢复不同：前者靠 Trellis/jj/文档，后者靠 Temporal/数据库/持久资产，不相互替代。
