# Agent 时代的项目开发正确性保障指南

整理日期：2026-08-25  
适用范围：使用 Codex、Claude Code、Cursor、Aider、OpenHands 或其他 LLM/Agent 辅助开发的软件、算法及多模型工程项目。

## 0. 最高优先级开发宪法（P0）

本节是全文的前置门和覆盖层。后续章节描述“如何做”，本节规定“任何时候都不能省略什么”。在不违反 System/Developer 指令、安全与权限边界、用户当前明确指令及适用 `AGENTS.md` 的前提下，本节优先于本文后续章节。无法判断冲突如何消解时，不得静默选择、自行扩大权限或猜测，必须先查证，并对会受影响的高风险分支启动 `grill-me`。

P0 的执行顺序是：

```text
先查证事实
 -> grill 关键歧义
 -> 固化任务契约
 -> 建立 Git/jj 可回滚锚点
 -> 主 Agent 编排并行工作
 -> 小步实现
 -> 主动测试与独立复核
 -> 人类决策门
 -> 记录结论、风险和下一步
```

### 0.1 一个主 Agent 编排多个 Sub-agent

复杂任务采用“一个主 Agent 负总责、多个 Sub-agent 做边界清晰的并行工作”的模式。Sub-agent 是并行执行单元和证据提供者，不是责任转移工具。

主 Agent 必须负责：

- 维护唯一的项目目标、当前计划、依赖关系和验收标准；
- 判断哪些工作可以并行，给每个 Sub-agent 明确且互不冲突的任务契约；
- 控制并发数量、上下文范围、写入权限和结束条件；
- 汇总不同结论，处理冲突和不确定性；
- 亲自复查关键文件、Diff、测试结果和实验产物；
- 对最终交付、事实准确性、未解决风险和对人类的汇报负责。

满足以下任一条件时，应优先考虑 Sub-agent：

- 存在两个以上相互独立、边界清晰的工作流；
- 查资料、查文件、跑实验、跑测试、写汇报等工作可以与主线并行；
- 需要实现者之外的独立审查、反例搜索或结果复算；
- 单个任务会长时间等待外部命令、评估或数据处理。

以下情况不应为了“多 Agent”而强行拆分：

- 任务很小，编排成本高于执行成本；
- 子任务强顺序依赖，后一步无法在前一步完成前产生有效结果；
- 多个 Agent 必须同时修改同一文件、同一接口或同一共享状态；
- 任务边界尚未 grill 清楚，拆分只会放大错误假设。

模型和任务分配遵循：

- 可用时，复杂推理、代码实现、实验分析和独立审查优先使用 `GPT-5.6 Sol` Sub-agent；
- 简单检索或机械任务可选择更快、更经济的模型；
- 指定模型不可用时，主 Agent 可以选择能力相当的替代项，但必须在汇报中说明；
- 不按“Agent 越多越好”分配，而按独立工作量、风险和可验证收益分配。

每个 Sub-agent 一次只承担一个原子、可验证任务，并至少获得以下任务契约：

```yaml
role: 本 Agent 的角色
goal: 唯一交付目标
context: 完成任务所需的最小上下文
allowed_scope: 可读取、可修改的范围
non_goals: 明确不做的事情
inputs: 输入和依赖
outputs: 文件、结论或实验产物
acceptance: 可执行的完成标准
tests: 必须运行的验证
write_isolation: 工作区、change、分支或只读约束
report: 证据、未知项、风险和建议
```

并发写入必须隔离：

- 只读检索、资料研究和日志分析可以共享工作区并行执行；
- 写任务默认分配互不重叠的文件范围；无法保证时，使用独立的 `jj workspace/change` 或 Git worktree/branch；
- 禁止多个 Agent 在同一工作副本中同时修改相同文件或执行相互影响的仓库状态操作；
- Sub-agent 不得自行扩大范围、接受业务风险、发布生产版本，或未经主 Agent 允许继续嵌套委派；
- 主 Agent 是唯一的整合者，整合后必须重新检查全量 Diff、冲突、测试和验收条件；
- Sub-agent 的“已完成”只表示候选结果，不等于项目完成。

“一次任务只解决一个可验证问题”指每个 Agent 的任务必须原子化，不禁止多个互不依赖的原子任务在隔离条件下并行。

### 0.2 Agent 八荣八耻

| 耻 | 荣 | 强制执行含义 |
|---|---|---|
| 暗猜接口 | 认真查阅 | 先查定义、调用方、测试、Schema 和官方文档，再讨论或修改接口 |
| 模糊执行 | 寻求确认 | 影响验收、架构、安全或不可逆结果的歧义必须确认 |
| 盲想业务 | 人类确认 | 业务语义、优先级、风险接受和最终取舍由人确认 |
| 创造接口 | 复用现有 | 先全库搜索已有抽象、工具和约定；新接口必须证明必要性 |
| 跳过验证 | 主动测试 | 主动运行与风险相称的静态检查、测试、评估和人工抽样 |
| 破坏架构 | 遵循规范 | 尊重模块边界、依赖方向、ADR、AGENTS.md 和发布门禁 |
| 假装理解 | 诚实无知 | 明确区分事实、推断和未知项，不伪造成功、日志、引用或结论 |
| 盲目修改 | 谨慎重构 | 修改前查调用链和现有 Diff；重构要小步、可测、可回滚 |

这八条不是口号。任何任务交付都必须能指出“查了什么、确认了什么、复用了什么、测了什么、还不知道什么、如何回滚”。缺少证据时，状态只能是“未验证”或“部分完成”。

### 0.3 人类调度者的三荣三耻与责任

人类负责人不是旁观者，而是目标、业务真相和风险接受的最终责任人。

| 耻 | 荣 | 人类负责人需要承担的动作 |
|---|---|---|
| 以人类幻觉为耻 | 以动手搜索为荣 | 对关键判断要求代码、数据、实验或一手资料证据；不能把直觉直接当成需求事实 |
| 以傲慢自大为耻 | 以 Agent 友好为荣 | Agent 反复出错时，先检查任务契约、AGENTS.md、工具、测试和反馈是否足够，再改进系统 |
| 以上下文膨胀为耻 | 以简化操作为荣 | 把稳定知识沉淀为短文档、脚本、模板和检查器；删除或更新过期、重复、互相矛盾的上下文 |

人类负责人必须亲自确认：

- 项目章程、业务定义、成功指标和明确非目标；
- 架构边界、数据含义、安全隐私、预算和风险接受；
- 需求冲突时的优先级；
- 破坏性操作、外部副作用、数据迁移和生产发布；
- 阶段验收以及继续、转向、暂停或回滚决定。

主 Agent 必须在以下触发点提醒人类当前职责，而不是机械地每轮复读口号：

- 项目启动或目标变化时，提醒确认章程、指标和非目标；
- 架构、业务、数据、安全、成本边界存在歧义时，逐项 grill；
- 同类错误重复发生时，建议补充 AGENTS.md、测试、脚本或小工具；
- 上下文变长、过期或互相冲突时，建议压缩并沉淀到代码库；
- 破坏性操作、里程碑验收和发布前，提醒完成明确的人类决策门。

### 0.4 Git + jj：把隐式、不可恢复的流程变成显式、可回滚的工程系统

正式开发不得在版本控制之外进行。Git 是远端协作和生态兼容的基线；条件允许时，优先试用 jj 管理本地 change、操作历史和回滚。采用 jj 不代表放弃 Git，也不代表任何操作都能自动恢复。

开始修改前必须：

- 确认真正的仓库根目录，不得在不明确的父目录随意初始化仓库；
- 检查 `git status` 或 `jj status`、当前 Diff、已有未提交修改和未解决冲突；
- 将已有修改视为他人或用户资产，不覆盖、不清理、不擅自纳入当前任务；
- 新项目在第一行正式业务代码产生前建立仓库；现有项目引入 jj 前先确认兼容方式和回滚方案；
- 记录 Git、jj 版本以及仓库是纯 Git、纯 jj 还是 colocated Git/jj。

推荐采用 colocated Git/jj 工作区，让 Git 工具和 jj 共用工作副本。jj 官方文档说明：新建 Git-backed 仓库时 colocated 是当前默认模式；两类命令可以共存，但混用会增加状态理解成本。因此约定：

- 主要使用 jj 执行会改变历史或工作副本状态的操作，Git 默认只做只读检查和远端兼容；
- 必须混用可变 Git 命令时，操作前后都运行 `jj status`、`jj diff` 和必要的 `git status`；
- 每个 Task 对应一个单一目的的 change/commit，先写清描述，再实现、测试和审查；
- 新功能、重构、依赖升级和机械格式化分别记录，不堆进同一个 change；
- 使用 `jj op log` 查看仓库操作历史；恢复前必须精确确认目标操作、此后的操作和影响范围；
- `jj undo` 仅用于最近一次操作确实是需要撤销的本方操作，且其后没有用户或其他 Agent 操作的场景；
- 共享仓库不得盲目 `jj undo`；应通过 operation ID 制定精确恢复方案并复核结果；
- `jj op log` 是恢复机制而非独立备份；关键成果仍需可靠提交、检查点和远端或其他独立备份；
- 本地操作日志不能撤销已经发送的消息、外部 API 副作用、数据库破坏或已发布内容，这些必须有单独回滚方案；
- 禁止未经授权的强制推送、公开历史重写、`git reset --hard`、`git clean` 或大范围清理；
- 发布或交接前必须保证没有未解决冲突，变更描述清楚，测试证据与具体 change/commit 可对应。

最小 jj 工作闭环：

```text
jj status / jj diff / jj log
 -> 为当前任务建立并描述 change
 -> 小步修改
 -> 测试与评估
 -> jj diff + 范围审查
 -> 独立复核或人类验收
 -> 形成下一条空 change 或进入发布门
 -> 出错时先看 jj op log，再选择精确恢复方式
```

具体命令以项目锁定的 jj 版本和 `jj help` 为准。团队首次采用或升级 jj 时，先在非关键仓库演练 init、workspace、bookmark、push、undo 和 op restore，再写入项目操作手册。参考 jj 官方的 [Git compatibility](https://docs.jj-vcs.dev/latest/git-compatibility/) 与 [Operation log](https://docs.jj-vcs.dev/latest/operation-log/)。

### 0.5 Skill 使用与沉淀准入

Skill 不是越多越好。只有以下类型值得优先引入或沉淀：

1. **领域知识型**：补足团队或通用 Agent 明显缺少的专业知识；
2. **生活/操作痛点型**：消除高频、繁琐、容易出错的人工步骤；
3. **流程模板型**：把稳定、重复的流程固化为可执行模板；
4. **核心工程型**：项目构建、测试、评估、发布、回滚、安全等不可缺少的少量核心能力。

引入或创建 Skill 前必须回答：

- 它补足了什么明确缺口，现有文档、脚本或工具为什么不够；
- 这个问题是否重复出现，Skill 能否带来可测量的时间、质量或风险收益；
- 需要哪些权限、外部依赖和维护责任；
- 输出如何测试，失败如何降级；
- 是否存在更简单的脚本、模板、AGENTS.md 规则或直接操作。

执行规则：

- 一个任务只加载覆盖当前缺口的最小 Skill 集；
- 使用前完整阅读适用说明，只加载任务需要的引用和资源；
- Skill 不得扩大用户授权，也不得替代测试、来源核验和人工决策；
- Skill 对实现产生实质影响时，在交付中说明影响和验证方式；
- 一次性、简单或能够直接查库解决的问题，不新建 Skill；
- 稳定流程重复出现且边界已经验证后，再沉淀 Skill；为其保留示例、验收、版本和维护人；
- 定期删除、合并或更新过期 Skill，避免能力目录和上下文持续膨胀。

#### 0.5.1 已准入核心 Guardrail：`stop-that-shit`

项目将 [`lennney/stop-that-shit`](https://github.com/lennney/stop-that-shit) 作为少量核心工程插件之一，用于约束非必要范围扩张、无依据的 Sub-agent、依赖与哈希，以及审阅任务中的越权写入。当前准入基线为插件 `0.1.0`、审计提交 `8a424ab587f20d3d2ea6787f233740c833ba8476`；升级时必须重新审查 manifest、Hook、权限、隐私说明和测试结果，并同步更新本节。

Codex 中按任务显式选择模式：

```text
$stop-that-shit review -- 审阅并汇报，不修改文件。
$stop-that-shit answer -- 回答问题，不修改文件。
$stop-that-shit monitor -- 监控并汇报，不修改目标状态。
$stop-that-shit change -- 只完成请求内容及有证据证明的必要后果。
$stop-that-shit lock change files=path/a|path/b -- 在已查明完整边界时锁定写入文件。
```

执行约束：

- 2026-09-09 用户明确：避免过度开发、绕路和 token 浪费。日常不做全量 SHA256 校验，不搭建输入/模型/Prompt 哈希体系；保留原交付校验文件，不重算。使用资产 ID/版本、相关测试和差异审查；按需加载 Skill，不为简单任务增设流程。
- `review`、`answer`、`monitor` 默认只读；`change` 也不授权顺手重构或扩大目标；
- Guard 初始处于 `unconfirmed` 观察态，必须由明确模式武装；不得把“插件已安装”误报为“动作已拦截”；
- 首次安装、升级或 Hook 内容变化后，必须重启 Codex，并由人类负责人在全新 CLI TUI 中运行 `/hooks`，逐条审阅并信任 `UserPromptSubmit` 与 `PreToolUse`；不得自动绕过该信任门；
- 截至 2026-08-25，Codex IDE extension 官方明确不支持 Plugins；Cursor/VS Code 侧栏可以使用 Codex，但不会加载本插件。需要强制 Hook 时，应从 IDE 集成终端进入本仓库并运行 Codex CLI；侧栏会话只能把同一规则作为人工遵循的治理约束；
- 插件只在受支持且已启用的 Hook 路径上提供本地 Guardrail，不是安全沙箱；它不得替代任务契约、权限边界、Git/jj 隔离、测试、主 Agent 复核或人类决策；
- 当前版本声明不联网、不上传提示词或工具内容，只在宿主提供的插件数据目录保存元数据型契约和审计记录；升级后须重新确认；
- 需要诊断时使用 `$stop-that-shit status`、`runtime` 和 `explain evt_...`，不得为了证明插件存在而重复无收益的审计循环。

### 0.6 将 grill-me 内化为项目认知对齐与关键歧义消除协议

`grill-me` 的目标不只是拦住高风险歧义，还要通过持续追问项目细节，让人类负责人和 Agent 建立同一份领域模型、术语表、数据认知与成功标准。问题数量不是目标；消除无声假设、形成可执行的共同理解才是目标。

出现以下情况必须启动：

- 新项目、新 Milestone、重大方案或架构实现即将开始；
- Agent 尚不能用项目自己的语言准确解释目标用户、业务流程、核心实体、术语和边界；
- 数据来源、样本单位、类别含义、标注规则、数据切分、质量问题、评价指标或失败代价尚未对齐；
- 运行环境、性能目标、预算、部署方式、人工复核流程、成功标准或非目标尚未对齐；
- 接口、数据、业务语义、验收、安全、隐私、成本、部署或权限存在关键歧义；
- 不同答案会导致明显不同的架构、不可逆操作或大量返工；
- 事实无法从代码库、测试、数据、日志、ADR 或权威资料中查得；
- 人类明确要求 `grill-me`。

执行协议：

1. **先查再问**：能查代码库、配置、测试、日志或权威资料回答的，直接查并给出证据，不能把检索工作推回给人；
2. **项目知识优先**：优先询问能最大幅度提升共同理解的领域问题，而不只询问技术选型；典型顺序是目标与用户、领域术语、输入数据、期望输出、评价指标、失败处理、运行与交付边界；
3. **一次一问**：每轮只提出一个当前信息增益最高的问题，等待回答后再继续。本项目已固定一次一问的兼容版本；若未来上游升级为“一轮询问整个 frontier”，仍以本条覆盖；
4. **给出上下文**：说明已经查到的事实、当前未知项、为什么该问题会改变理解或方案，并在适合时给出建议默认值及主要取舍；
5. **阻塞相关分支**：等待确认时暂停依赖该答案的高风险或不可逆工作，但继续安全、独立、只读的工作；
6. **访谈本身无状态**：显式 `/grill-me` 期间不修改项目文件、不实施方案；达到共同理解并由人类确认结束后，再由主 Agent 把已确认结论写回；
7. **写回代码库**：确认后的答案必须沉淀到项目章程、领域词汇表、数据说明、任务契约、ADR、Schema、测试或风险登记表，不能只留在聊天中；
8. **持续到收敛**：逐个处理知识缺口和关键歧义，直到双方对目标、术语、数据、范围、验收和约束形成可执行共识。

以下情况不应启动冗长 grill：

- 答案能够直接从仓库或权威资料确定；
- 差异不会实质改变结果，且存在安全、可逆、符合现有规范的默认值；
- 当前只是只读调查，尚未进入依赖该决定的实施；
- 问题只是在转移 Agent 本应完成的搜索、测试或分析工作。

退出 `grill-me` 的标准不是“聊了足够久”，而是双方能够用同一套项目语言复述目标、数据、主要流程、成功与失败，并且关键决策已经可执行、可验证、可追溯；仍未知的内容已有负责人、验证方法和截止点。

### 0.7 诚实交付的最小证据

所有 Agent 的完成声明必须同时说明：

- 实际修改和未修改的范围；
- 运行过的测试、实验或评估及其结果；
- 未运行项目及原因；
- 仍存在的假设、风险和未知项；
- 对应版本、change 或可恢复检查点；
- 是否需要人类验收或下一项决策。

检索结果、Sub-agent 意见、模型自评和“看起来正确”均不能替代确定性验证。无法证明时，应诚实报告“未知”或“尚未验证”，不得伪造理解、测试结果或完成状态。


## 1. 核心结论

Agent 可以显著加快代码实现，但不能自行保证项目方向、实施过程和最终结果正确。可靠做法不是寻找一个“永远不犯错”的 Agent，而是在 Agent 外部建立一套工程控制系统：

```text
目标与约束
  -> 可执行验收标准
  -> 最小端到端系统
  -> 小步任务
  -> Agent 实现
  -> 自动测试与独立评估
  -> 人工验收门
  -> 版本化与回滚
  -> 下一轮
```

项目正确性可以分为三层：

| 层次 | 核心问题 | 主要保障手段 |
|---|---|---|
| 方向正确 | 是否在解决正确的问题 | 项目章程、成功指标、非目标、风险原型 |
| 过程正确 | 每一步是否仍服务原目标 | 分层计划、任务契约、小型 Diff、阶段验收门 |
| 结果正确 | 整体和细节是否满足要求 | 分层测试、固定评估集、可追溯运行、发布门禁与回滚 |

最终目标是让 Agent 高速工作，同时让目标、过程、接口、结果和发布分别受到外部约束。

## 2. 如何确保项目起步正确

### 2.1 建立项目章程

在大量写代码之前，用一页文档固定以下内容：

- 目标用户及其真实问题；
- 最核心的使用流程；
- 成功指标和失败条件；
- 明确不做的事情；
- 时间、算力、部署、许可证、隐私和兼容性约束；
- 必须由人确认的高风险决策。

推荐模板：

```yaml
problem: 要解决的真实问题
users: 目标用户
primary_workflow: 最重要的一条用户流程
success_metrics:
  - 可量化指标一
  - 可量化指标二
non_goals:
  - 当前阶段不处理的内容
constraints:
  - 算力、部署、时间、许可等约束
critical_risks:
  - 如果不成立会推翻方案的关键假设
human_decisions:
  - 必须由负责人批准的事项
```

项目章程不是宣传文档，而是以后判断需求是否跑偏的最高层依据。

### 2.2 先定义验收，再选择技术

每个核心能力必须转化为可观察、可执行的验收条件。避免使用“足够智能”“体验很好”“准确率较高”等无法直接验证的描述。

验收定义至少应包含：

- 标准输入；
- 期望输出及 Schema；
- 正常路径；
- 失败和证据不足路径；
- 精度、性能、成本和资源阈值；
- 可追溯性和恢复要求。

验收条件应反过来决定架构和技术，而不是先选择热门模型、Agent 框架或数据库，再为它们寻找用途。

### 2.3 先完成最小纵向切片

项目的第一个版本应覆盖一条真实的端到端流程，而不是分别建设大量尚未连接的模块。这种版本也称 Walking Skeleton。

它可以功能简陋，但必须包含：

```text
真实输入
 -> 核心处理
 -> 持久化或中间状态
 -> 最终输出
 -> 错误处理
 -> 最小验证
```

最小纵向切片能够尽早暴露以下高风险问题：

- 数据与任务并不匹配；
- 模型指标无法满足业务需求；
- 接口和数据流设计错误；
- 推理延迟、成本或显存无法接受；
- 部署环境不能支持选定技术；
- 最终结果无法被用户使用或验证。

### 2.4 优先验证最危险的假设

不要优先实现最容易展示的页面，应先验证一旦失败就会推翻项目的假设。例如：

- 真实数据是否足够；
- 模型在目标场景是否有效；
- 关键外部服务能否稳定访问；
- 延迟和成本是否可接受；
- 物理量测是否具备标定条件；
- 用户是否真的需要该工作流。

这种验证可以使用一次性原型，但原型结论必须记录，不能把演示成功直接等同于生产可行。

### 2.5 冻结外部评价锚点

在大规模开发前保存：

- 固定验证集和困难样本集；
- 当前基线指标；
- 标准输入输出样例；
- 关键用户场景；
- 性能、成本和资源预算；
- 已知失败案例。

以后无论重构、换模型还是更换 Agent，都应在相同评价锚点上比较。评价集不能跟着实现随意变化，否则可能出现代码越来越多、实际能力反而下降的情况。

## 3. 如何确保实施过程按照计划推进

### 3.1 使用三级计划

```text
Roadmap
  描述为什么做、最终交付什么

Milestone
  描述本阶段需要证明什么

Task
  描述一次具体修改及其验收方法
```

Roadmap 不应直接拆成几十个代码任务；每个 Milestone 都应对应一个可验证结果，例如“完成固定数据集上的端到端基线”，而不是“完成后端开发”。

### 3.2 为 Agent 提供任务契约

每次 Agent 任务应尽量使用固定结构：

```yaml
goal: 本任务唯一需要得到的结果
context: 必需的背景和当前状态
inputs: 输入及前置条件
outputs: 文件、接口或运行产物
allowed_scope: 允许修改的目录和模块
non_goals: 明确不处理的内容
contracts: 必须遵守的接口和数据结构
acceptance: 可执行的验收条件
tests: 必须运行的测试或评估命令
risks: 可能影响架构的假设
rollback: 出现问题时如何恢复
```

任务越模糊，Agent 越容易自行补充假设、扩大范围或进行未经授权的重构。

### 3.3 执行固定闭环

每个任务遵循：

```text
Plan
 -> Todo
 -> Execute
 -> Observe
 -> Test
 -> 与验收标准比较
 -> Update Plan
```

“完成”必须由证据决定，而不是由 Agent 自己宣布。至少检查：

- 测试是否通过；
- 输出是否符合 Schema；
- 指标是否达到阈值；
- 是否修改了任务范围外的文件；
- 是否引入了新的依赖或副作用；
- 文档与实现是否一致；
- 是否出现无法解释的行为变化。

### 3.4 控制单次改动规模

推荐遵循：

- 一次任务只解决一个可验证问题；
- Diff 尽量小且容易审查；
- 每个提交能够独立构建或测试；
- 架构决策通过 ADR 单独记录；
- 新功能、重构和依赖升级尽量分开；
- 大规模机械改动与逻辑修改分开提交。

这里的“一次任务”指每个 Agent 只承担一个原子任务；多个互不依赖的任务可以按 0.1 节在隔离条件下并行。

小步开发的意义是能够准确定位哪次修改造成回归，并能低成本撤销。

### 3.5 设置阶段验收门

每个 Milestone 结束时进行一次 Drift Review：

- 当前工作是否仍服务项目章程；
- 目标、用户或约束是否发生变化；
- 哪些关键假设已经被数据否定；
- 新增复杂度是否带来可测量收益；
- 是否出现未计划的新系统或新依赖；
- 本阶段是否真正产生可运行产物；
- 是否应该继续、调整方向、暂停或回滚。

不通过阶段验收门时，应修改计划或修复问题，而不是继续添加代码掩盖偏差。

### 3.6 明确 Agent、确定性系统和人的职责

| 主体 | 适合负责 | 不应单独决定 |
|---|---|---|
| Agent | 编码、局部重构、生成测试、分析失败、整理文档 | 项目目标、风险接受、最终发布 |
| 确定性系统 | Schema 校验、测试、指标计算、权限、状态保存、发布门禁 | 模糊业务价值判断 |
| 人 | 目标、架构边界、数据含义、风险、验收和发布 | 重复性的机械实现 |

另一个 Agent 可以参与审查，但“另一个模型认为没有问题”不能代替测试、固定数据评估或人工抽样。

## 4. 项目变大后如何保证整体和细节正确

### 4.1 让代码库成为长期记忆

重要知识不能只保存在聊天历史中。推荐至少维护：

```text
docs/
  PROJECT_CHARTER.md
  ARCHITECTURE.md
  ROADMAP.md
  adr/
contracts/
  api/
  events/
tests/
  unit/
  contract/
  integration/
  e2e/
eval/
  frozen_dataset/
  golden_cases/
  regression/
AGENTS.md
```

其中：

- `PROJECT_CHARTER.md` 保存方向锚点；
- `ARCHITECTURE.md` 保存当前系统边界和数据流；
- ADR 保存重要决策、备选方案和取舍；
- `AGENTS.md` 告诉 Agent 如何构建、测试、修改和验收；
- 测试和评价集是可执行的事实来源。

仓库根目录确认后，应尽早创建短小、可维护的项目级 `AGENTS.md`。它只保存稳定且可执行的规则；重复错误应优先转化为测试、脚本或检查器，过期说明应及时更新或删除。

### 4.2 使用任务局部工作集

大型项目中，不应要求 Agent 一次理解整个仓库。每次只构造当前任务所需的工作集：

- 当前目标和约束；
- 入口文件；
- 接口和实现；
- 调用方和下游消费者；
- 对应测试；
- 当前 Git/jj 状态与 Diff；
- 相关 ADR；
- 未解决问题。

代码库负责长期记忆，Agent 上下文只负责当前任务。这比不断扩大对话上下文更可靠。

### 4.3 用契约隔离复杂度

每个模块应明确：

- 输入、输出和错误类型；
- 前置条件和后置条件；
- 超时和重试策略；
- 是否幂等；
- 是否产生外部副作用；
- 数据、模型和接口版本；
- GPU、数据库或网络依赖；
- 允许和禁止依赖的模块。

只要契约稳定，Agent 修改一个模块时不需要完整理解所有内部实现。

### 4.4 建立分层测试体系

| 层次 | 主要验证内容 |
|---|---|
| 静态检查 | 类型、格式、依赖规则、安全规则 |
| 单元测试 | 函数、类和局部算法 |
| 契约测试 | 模块输入输出是否兼容 |
| 集成测试 | 数据库、队列、模型服务和外部接口组合 |
| 端到端测试 | 真实用户流程是否完整可用 |
| 回归测试 | 历史正确能力是否被破坏 |
| 性能测试 | 延迟、吞吐、显存、并发和成本 |
| 故障恢复测试 | 超时、重试、断线、崩溃和任务恢复 |
| 业务验收 | 最终结果是否解决项目章程中的问题 |

测试不是越多越好，而是关键边界、失败路径和高风险功能必须有证据覆盖。

### 4.5 AI 项目需要单独的模型评价体系

除普通软件测试外，还应保存：

- 固定模型和数据版本；
- 总体及逐类指标；
- 困难样本、负样本和分布外样本；
- 置信度校准和拒识率；
- 人工复核率；
- 推理延迟、显存和成本；
- 模型更新前后的回归对比；
- 提示词、推理参数和外部工具版本。

LLM/VLM 评价不能只看少量展示样例。需要固定数据、结构化评分、人工抽样以及对失败案例的长期回归。

### 4.6 保存可追溯运行证据

每次重要运行至少保存：

```text
代码提交版本
配置版本
模型与权重版本/资产 ID
数据版本
输入资产 ID 与版本
关键中间产物
日志和指标
最终结果
人工修改记录
```

如果不能回答“这个结果由哪份代码、哪个模型、哪些配置和哪些输入产生”，就很难在大型项目中判断结果是否正确。

### 4.7 建立发布门禁和回滚能力

可靠发布至少要求：

```text
关键测试通过
+ 固定评估集没有不可接受的回归
+ 数据迁移经过验证
+ 模型和配置版本可切换
+ 旧版数据或产物仍可兼容
+ 线上指标可以监控
+ 存在明确回滚步骤
```

Agent 可以准备发布，但不应绕过门禁直接修改生产环境。

## 5. 推荐的项目治理文件

### 5.1 ADR

重要架构决定使用 Architecture Decision Record 保存：

```text
标题
状态：proposed / accepted / superseded
背景
决策
备选方案
选择理由
后果与风险
验证方式
```

ADR 不需要很长，重点是防止未来的 Agent 或开发者不知道当初为什么这样设计。

### 5.2 Definition of Done

项目应维护统一完成标准：

- 实现满足任务验收条件；
- 新增或更新测试；
- 所有相关测试通过；
- 无任务范围外修改；
- 接口和文档同步；
- 指标没有不可接受的回归；
- 日志、错误和异常路径可观察；
- 产物可重现；
- 必要时提供迁移和回滚方案。

### 5.3 风险登记表

持续记录：

| 风险 | 发生概率 | 影响 | 当前证据 | 缓解方案 | 负责人 | 状态 |
|---|---:|---:|---|---|---|---|

Agent 可以发现和更新风险，但风险接受必须由项目负责人决定。

## 6. 在 YOLO26 + VLM 管网项目中的具体应用

### 6.1 项目章程示例

```text
目标：
从 CCTV 视频生成可追溯的缺陷事件和检测报告。

核心指标：
事件级 Recall、Precision、人工复核率、处理速度、每小时视频成本。

非目标：
不让 VLM 逐帧控制检测；
不让单目 VLM 猜毫米尺寸；
第一阶段不实现机器人自主控制。
```

### 6.2 最小纵向切片

```text
一个真实 CCTV 视频
 -> YOLO26 检测
 -> ByteTrack/BoT-SORT 跟踪
 -> DefectEvent 聚合
 -> VLM 事件级复检
 -> 状态机校验
 -> 结构化报告
```

第一阶段应证明这条链路能够运行、恢复和追溯，而不是立即建设复杂多智能体平台。

### 6.3 核心契约

```text
YOLODetector
输入：Frame
输出：Detection[]

Tracker
输入：Detection[]
输出：Track[]

EventAggregator
输入：Track[]
输出：DefectEvent[]

VLMReviewer
输入：DefectEvidencePackage
输出：ReviewDecision

ReportGenerator
输入：ConfirmedFact[]
输出：InspectionReport
```

VLM 只能复核证据和生成受约束的语义结论；框、轨迹、掩膜、几何数值和最终业务状态分别由对应模块负责。

### 6.4 固定评价锚点

至少冻结：

- Sewer2403 固定验证集和数据划分；
- 五类 YOLO26 当前基线；
- 17 类历史参考结果；
- BX、FS、PL 困难案例；
- 空管道、污渍、反光、模糊和水雾负样本；
- 固定事件聚合和 VLM 复检测试包；
- 事件级指标、人工复核率和成本预算。

### 6.5 开发顺序

当前实施只遵循[总体开发计划](DEVELOPMENT_PLAN.md)的 M0～M5，不在治理文档重复维护任务表。已有五类权重不再训练；LLM/VLM 使用 API，本地部署后端与视觉工具。原先 E0～E9 的训练/蒸馏顺序不再作为首版排期。

架构见[主方案](../vlm_review/VLM_YOLO_ARCHITECTURE_AND_RESEARCH_SUMMARY.md)，活动任务与交接由 Trellis 保存。总体计划已于 2026-09-09 获批；按任务范围实施，重新训练仍需用户另行决定。

## 7. 实际执行检查表

- [ ] 人类负责人已确认项目章程、成功指标、非目标和风险接受边界；
- [ ] 已先查代码、数据和权威资料，并通过 `grill-me` 消除会实质改变方案的关键歧义；
- [ ] 高风险假设已有验证计划；
- [ ] 验收标准可执行；
- [ ] 最小纵向切片已定义；
- [ ] 固定评价集和基线已保存；
- [ ] 已确认仓库根目录并启用 Git，jj 试点模式、版本、备份和恢复演练已明确；
- [ ] 主 Agent、Sub-agent、人工决策门及并发写入隔离方式已明确；
- [ ] 所需 Skill 已通过价值、权限、维护和最小集合审核。
- [ ] `stop-that-shit` 版本与提交已审计，插件已启用，两个 Hook 已由人类负责人逐条审阅并信任。

### 每个任务开始前

- [ ] 已搜索现有接口、实现、调用方、测试、ADR 和可复用工具；
- [ ] 目标、范围、非目标和输入输出契约清楚；
- [ ] 会改变实现结果的歧义已 grill 清楚或登记为阻塞项；
- [ ] 验收条件和测试命令明确；
- [ ] `git status` 或 `jj status`、当前 Diff、用户已有修改和冲突已检查；
- [ ] 每个 Agent 的任务原子化，允许修改范围、写入隔离和汇报格式明确；
- [ ] 仅加载了当前任务确实需要的最小 Skill 集。

### 每个任务完成时

- [ ] 验收条件均有可定位证据；
- [ ] 测试和评估已实际运行，未运行项及原因已说明；
- [ ] Sub-agent 产物已经主 Agent 独立复查，不以模型意见代替测试；
- [ ] Git/jj 状态和全量 Diff 已检查，没有越界、混杂或冒领修改；
- [ ] 文档、接口、ADR 和 grill 结论已同步到代码库；
- [ ] 事实、推断、未知项、新风险和未解决问题已诚实区分；
- [ ] change/commit 与测试证据对应，精确恢复步骤已验证；
- [ ] 需要的人类验收或下一项决策已明确。

### 每个阶段结束时

- [ ] 人类负责人已重新确认项目章程、业务含义、风险和继续方向；
- [ ] 与冻结基线重新比较；
- [ ] 检查复杂度、Sub-agent 和 Skill 是否带来可测量收益；
- [ ] 检查关键假设是否仍然成立；
- [ ] 完成端到端和恢复测试；
- [ ] 过期或膨胀的上下文已压缩，稳定经验已沉淀为短文档、测试、脚本或核心 Skill；
- [ ] 明确继续、调整、暂停或回滚决定。

### 发布前

- [ ] 全部发布门禁通过；
- [ ] Git/jj 无未解决冲突，目标 change/commit、模型、配置和数据版本完整可追溯；
- [ ] 线上监控和告警有效；
- [ ] 数据迁移、外部副作用、兼容性和独立备份已验证；
- [ ] 回滚命令、精确目标和负责人明确；
- [ ] 人工验收及生产授权已完成。

## 8. 最值得长期坚持的规则

1. 查证先于猜测；能查库就直接查，关键歧义再按 `grill-me` 一次一问；
2. 人类先定义什么叫正确，并对业务真相、风险接受和最终发布负责；
3. 把目标转换成测试、指标、Schema、固定数据和明确的人类决策门；
4. 一个主 Agent 负责编排与整合，每个 Sub-agent 只承担一个边界清晰的原子任务；
5. 并行工作必须有可验证收益，写入必须隔离，主 Agent 必须复核最终全量 Diff；
6. 认真查接口、复用已有能力、主动测试、遵循架构、诚实报告未知、谨慎重构；
7. 正式开发必须进入版本控制；Git 是兼容基线，jj 是经过演练和记录的受控工作流；
8. 可回滚必须由精确恢复步骤和独立备份证明，不能只因为使用了 Git 或 jj 就宣称成立；
9. 代码库、测试、ADR、任务状态和版本记录是长期事实，聊天上下文不是；
10. Agent 不应同时充当实现者和唯一验收者，Sub-agent 共识也不能替代确定性验证；
11. Skill 少而精，只补领域缺口、解决高频痛点、模板化稳定流程或承载核心工程能力；
12. 人类和 Agent 都应主动搜索、改进 Agent 友好性并压缩过期上下文；
13. 项目越大，越依赖模块契约、局部工作集和冻结评价锚点，而不是单个模型理解全局；
14. 先保证可运行、可恢复和可验证，再增加复杂度与自主性；
15. 新 Agent、Skill、模型或工具必须证明带来可测量收益，而不是因为流行就加入架构。

一个可靠的 Agent 辅助开发系统应当满足：

```text
Agent 能高速工作，
但目标由章程约束，
过程由计划和状态约束，
接口由 Schema 约束，
结果由测试和数据约束，
发布由门禁约束，
错误由版本和回滚兜底。
```

只要这些外部约束存在，即使更换 Agent、LLM、框架或团队成员，项目仍然能够沿着可验证的方向稳定推进。
