# T08 设计边界

复用一次顺序解码的 GPU Activity，按有限帧批次原子提交观测/聚合状态/进度，并发送 heartbeat。重试重新顺序解码原文件以恢复准确帧索引与 PTS，但跳过已提交帧的 PNG 写入和 GPU 推理；正常运行不逐块从头解码。这比预存全视频 PNG 节约空间，也不引入尚未验证的关键帧 seek 索引。恢复仍有已完成前缀的 CPU 解码成本，明确记录。

Temporal 是唯一调度者。视频工作流依次初查 → 原帧证据持久化 → 有预算的逐代表帧条件复检 → 决策/报告。工作流历史仅传 run/帧索引/小摘要，完整逐帧观测、事件状态放 PostgreSQL。沿用现有 TaskSnapshot 的 processed_frames/processed_chunks 和 stage 字段，无第二业务状态机。

视频状态与逐批观测使用专用小表，沿用原 run pins/tool calls/step checkpoints。原子锁定任务与状态后提交，重复块读取已有状态，拒绝帧缺口/跨源/配置变化。最终化后禁止迟到批次改写。取消通过 Temporal 持久 Update 返回是否接受，等待活动停止再保存取消快照；进入 reporting 后明确拒绝取消，避免接受了却仍完成的竞态。已取消任务不由 start 复活。

代表帧取自 T07 的每事件最多 3 帧及周期审计帧。只保留选中原帧资产（父资产为原视频），不保存全帧 PNG；证据补建可单独恢复。复用 ImageReviewer 与图片规则逐帧复检，事件内意见冲突或建议改类不自动确认；多帧全部同意才确认。初始默认 32 次语义复核上限，运输重试另限 3 次；预算不足显式 partial，不能宣称正常。T09 再提供人工裁决与精细时间轴。

SEDD 与 Sewer2403 的固定样本按标注而非预测选择，前者作为外部来源、后者注明可能训练重叠。先核实类别定义与框格式，再冻结 manifest；最多 48 张总先导样本，不批量扫描全图片库调用 API。用户提供的 29 个视频共约 3:24:07，先完整跑 22.402 秒/561 帧录像，再用一段较长录像验证结果压缩；不把未知缺陷时间当真值。
